# Spec-Driven Development — Conventions

## Directory Layout

    specs/
      README.md           <- this file
      INDEX.md            <- auto-generated, do not edit manually
      <spec-id>.md        <- one per logical unit
      check-report-*.md   <- generated by /spec-check (optional)
      tests/
        INDEX.md          <- auto-generated
        <spec-id>.md      <- test spec, mirrors code spec

## Universal Rules

These apply to every command unless a command explicitly overrides them.

- **Handle lifecycle:** Close every spawned handle before the command ends.
- **Persistent spawns:** Keep the handle open and use send() for follow-up instructions; reuse across units instead of re-spawning.
- **Deprecated REQs:** Skip deprecated (strikethrough ~~REQ-XX-NNN~~) REQs in all commands unless explicitly told otherwise.
- **Ref exemptions:** Private (_prefix) functions are exempt from # Spec: refs. conftest.py and @pytest.fixture-decorated functions are exempt from # TestSpec: refs.
- **INDEX regeneration:** Any command that adds, removes, or renames a spec file must regenerate specs/INDEX.md (and specs/tests/INDEX.md for test specs).
- **Single responsibility:** Each command's primary write target is its designated artifact: /spec -> specs/, /testspec -> specs/tests/, /spec-impl -> src/, /spec-test -> src/tests/. Commands may also update cross-references (e.g., # Spec: refs in docstrings, parent spec frontmatter) as specified in their workflow. /spec-check and /spec-status are read-only.

## Spec ID Convention

    src/agent_loop.py       -> agent-loop
    src/rlm/kernel.py       -> rlm-kernel
    src/agent_context.py + src/agent_context_manager.py
                              -> context-management (unified spec)

Rule: if a spec covers multiple files, the ID is the feature name, not any single file name.

(This is a default; a project may override the ID scheme in its CONVENTIONS.md.)

## REQ ID Convention

Format: REQ-<ABBR>-<NNN>
- ABBR: 2-4 letter abbreviation of the spec ID (first letters of words)
- NNN: 3-digit zero-padded sequence, starts at 001

Examples:
    agent-loop         -> REQ-AL-001, REQ-AL-002, ...
    context-management -> REQ-CM-001, REQ-CM-002, ...
    rlm-kernel         -> REQ-RK-001, REQ-RK-002, ...

Rules:
- IDs are permanent. Never renumber. If a REQ is removed, mark it deprecated, do not reuse the number.
- One REQ = one atomic behavioral requirement.
- A REQ should be implementable by a developer without asking questions.

Deprecated REQs use strikethrough with a note: ~~REQ-AL-003~~ (deprecated 2026-09-12, replaced by REQ-AL-007)

## TC ID Convention

Format: TC-<ABBR>-<NNN> for unit, TC-<ABBR>-E2E-<NNN> for e2e.
Same ABBR as the parent spec.

Integration Tests share the unit TC namespace (TC-<ABBR>-<NNN>). They are distinguished by their section heading (## Integration Tests) in the test spec body, not by a distinct ID prefix.

## YAML Frontmatter (Code Spec)

    ---
    id: agent-loop
    version: 1.0
    status: draft | active | deprecated | archived
    weight: light | full
    source:
      - src/agent_loop.py
    tests:
      - specs/tests/agent-loop.md
    depends:
      - context-management
    created: 2026-09-12
    updated: 2026-09-12
    ---

Field rules:
- version: semver (major.minor), increment on breaking changes to the spec
  (version drift between README and a spec is informational — it signals one was updated after the other, not an error.)
- id: must match filename (minus .md)
- status: draft (being written) -> active (approved) -> deprecated -> archived
- weight: see Spec Unit Rules for light/full criteria
- source: list of source files this spec covers (required)
- tests: list of test spec files (required, even if empty list)
- depends: list of other spec IDs this spec depends on (required, can be empty list)
- created/updated: ISO dates, updated changes on every edit

## YAML Frontmatter (Test Spec)

    ---
    id: tests-agent-loop
    spec: agent-loop
    version: 1.0
    ---

- id: 'tests-' prefix + parent spec id
- spec: the parent spec id (required)

## Spec Body: Full Weight

    # <Human Readable Title>
    ## Purpose          <- 1-3 sentences. What and why.
    ## Requirements     <- REQ-XX-NNN entries, each with description
    ## Interface        <- Every public function/class with signature
    ## Behavior         <- Normal flow, Error cases, Edge cases
    ## Constraints      <- Hard rules
    ## References       <- Links to other specs, callers

## Spec Body: Light Weight

    # <Title>
    ## Purpose          <- 1 sentence
    ## Interface        <- Function signatures
    ## Requirements     <- 1-3 REQs

No separate Behavior/Constraints sections. They live inside the REQs.

## Test Spec Body

    # Test Spec: <Human Readable Title>
    ## Unit Tests
    ### TC-XX-NNN: <Name>
    - **Requirement:** REQ-XX-NNN
    - **Given:** <precondition>
    - **When:** <action>
    - **Then:** <expected outcome>
    - **Test file:** src/tests/test_<module>.py::test_<name>
    ## Integration Tests
    ### TC-XX-NNN: <Name>
    (same format as unit)
    ## E2E Scenarios
    ### TC-XX-E2E-NNN: <Name>
    - **Requirement:** REQ-XX-NNN, REQ-XX-NNN
    - **Given:** <precondition>
    - **When:** <action>
    - **Then:** <expected outcome>
    - **Test file:** src/tests/test_<module>_e2e.py::test_<name>

Each TC must reference at least one REQ via the 'Requirement:' field.

## Code Reference Format (in source docstrings)

Exact string, case-sensitive, one per line:

    # Spec: <spec-id>#<REQ-ID>

Example in a function docstring:

    def run_rlm_loop(kernel, context, config):
        """Execute the main RLM loop until answer is ready.

        # Spec: agent-loop#REQ-AL-001
        # Spec: agent-loop#REQ-AL-002
        """

Rules:
- Must be in the docstring (triple-quoted string), not a random comment
- No 'specs/' path prefix
- One REQ per line (a function satisfying 3 REQs has 3 lines)
- Every public function/class must have at least one # Spec: line
- Private functions (_prefix) do NOT need spec refs

## Test Reference Format (in test docstrings)

Exact string, case-sensitive:

    # TestSpec: <spec-id>#<TC-ID>

Example:

    def test_loop_stops_on_ready():
        """Verify loop exits when answer['ready'] is set.

        # TestSpec: agent-loop#TC-AL-001
        """

Rules:
- Must be in the test function docstring
- Every test function must have at least one # TestSpec: line
- conftest.py fixtures and @pytest.fixture decorated functions do NOT need refs

## Spec Unit Rules

- Default: one spec per source file
- Exception: feature spanning 2+ files -> one unified spec
- No spec for: __init__.py, conftest.py, pure re-export modules
- No spec for: test helper utilities, fixtures
- weight: light (module expected to be <50 LOC) or full (complex or >50 LOC modules)

## Code Conventions

Code style and structure rules live in `docs/CONVENTIONS.md`. Specs' Interface sections and `/spec-impl` must follow that file. If `docs/CONVENTIONS.md` does not exist, `/spec-impl` creates it by copying the starter template at `src/commands/_conventions-template.md`, then asks the user to confirm it before proceeding.

## Git Commit Convention

Format: <phase>: <topic> -- <detail>

Phases: spec, spec-review, testspec, impl, test, check, fix

Note: fix: is for manual user-initiated fixes outside the command workflow.

Examples:
    spec: agent-loop -- initial draft (REQ-AL-001..005)
    spec: agent-loop -- added REQ-AL-006 error recovery
    spec-review: agent-loop -- fixed 3 clarity issues
    testspec: agent-loop -- 12 TCs derived
    impl: agent-loop -- REQ-AL-001..003
    test: agent-loop -- 12 passed, 0 failed
    check: agent-loop -- 100% coverage, 0 orphans
    fix: agent-loop -- REQ-AL-004 timeout handling

Rules:
- Commit after each logical unit, not every line
- Never commit with failing tests
- Git log IS the development history
